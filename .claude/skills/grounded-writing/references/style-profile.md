# Grounded technical writing style

Use a restrained, plain technical register by default; a lighter tone is fine
for tutorials when the format suits it. Treat these patterns as a guide, not a
phrase bank. When the user supplies their own samples for the task, follow them.

## Voice and structure

- Start with what prompted the piece: a problem the author encountered, an
  assumption they tested, or something readers can now build. Use personal
  context when it explains the author's position, and only when the facts are
  supplied.
- Build the explanation from a familiar example to how it works and why that
  changes the result.
  Introduce jargon where it becomes useful; place examples, code, or measurements
  close to the claims they support. Use realistic examples for the audience.
- Show the reasoning, including when the result changes the initial assumption.
  Distinguish fact from inference, retain relevant
  measurement context, and explain what a limitation changes. Use contrast,
  surprise, and candid corrections only when the evidence supports them.
- Keep the direct, conversational tone: plain words, contractions, short focused
  paragraphs, and occasional standalone sentences for emphasis. Use first person only when grounded; address the
  reader when useful. Answer any rhetorical question promptly.
- End on a useful consequence, decision rule, or remaining insight. Land once;
  omit a recap or generic call to action unless the requested artifact needs it.

## Registers

| Register | Use when | Adjustment |
|---|---|---|
| Concise working note | Review comments, replies, status updates, short messages | Lead with the actionable point and necessary evidence, then stop. |
| Restrained long form | Essays, announcements, design documents, substantial emails, issue narratives, release notes | Lead directly, keep humour light, and use few rhetorical questions. |
| Playful explanation | Tutorials and deep technical walkthroughs | Allow occasional reader questions, candid asides, or an emoji while keeping explanation and evidence central. |

The requested format wins: preserve an email's shape, scannable release notes,
and a design document's decision and evidence sections. Do not manufacture an
introduction, conclusion, or blog structure for short working text.

## Language and editing

Follow the user's language and regional conventions unless requested otherwise.
Use technical vocabulary precisely and inline code for identifiers. Use headings,
lists, and tables when they expose the argument or make comparisons easier.

Remove generic scene-setting, marketing adjectives, unsupported superlatives,
fake anecdotes, and decorative catchphrases. Preserve intentional humour and
humility without accumulating rhetorical questions, fragments, asides, or emoji.
Read for natural rhythm; punctuation and emphasis should support clear sentences.
